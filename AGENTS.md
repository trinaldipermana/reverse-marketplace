# Agent instructions

1. **Keep changes within the assigned scope.** Read the issue and check its assignee and area labels before editing. If a fix needs changes in another owner’s area, record the dependency in GitHub and coordinate with that owner before editing their area.
2. **Send every change to `main` through a PR.** Push a separate branch and open a PR targeting `main`. Include the linked issue, a summary, and verification results. Use `Closes #123` when the PR fully resolves that issue. Leave the merge to a teammate after review.
3. **File findings where the team can see them.** Search for an existing GitHub issue before creating one. Record bugs, blockers, and contract or compatibility concerns as soon as you find them. Include what you observed, what you expected, how to reproduce it or verify the evidence, and which components or teammates are affected.
4. **Coordinate changes to shared contracts.** Before changing an API, payload, schema, or other interface another component relies on, link an issue that describes the proposed change, affected consumers, and the migration or rollout plan. Get agreement from affected owners before implementing a breaking change.
5. **Route issues with labels and assignees.** Use area labels that match the [team ownership table](./README.md#team-ownership), plus labels such as `bug`, `compatibility`, or `breaking-change` where relevant. Assign the agreed owner. Use `needs-triage` when ownership is unclear. If GitHub permissions prevent filing, labeling, or assigning, report the missing action and provide the details a teammate needs to complete it.

## MVP implementation rules

1. **Use the spec as the implementation baseline.** Read [INITIAL_SPEC.md](./INITIAL_SPEC.md) and distinguish confirmed requirements from proposed defaults and open decisions. If work depends on an unresolved API schema, migration owner, approval mode, or other open decision, raise or update a GitHub issue and coordinate with the affected owners.
2. **Respect service boundaries.** P1 owns the six conversation tool wrappers. P2 owns commerce operations and the atomic mock payment transaction. P3 calls the product APIs for the UI. P4 owns marketplace search and message delivery. P4 implements `SearchPost` for P2 discovery. It stays outside the conversation tool set.
3. **Agree on shared contracts before integrating.** Use shared domain types, tool names, lead states, and one ordered migration sequence. Capture request and response types, errors, event formats, and affected consumers in the linked issue as applicable. Get agreement from affected owners before implementing a breaking change.
4. **Keep enforcement in Go.** The model proposes actions through the six defined tools. Go validates policy and owns state changes, delivery, reservations, and payment. Preserve the lead states `active`, `reserved`, `escalated`, `paid`, and `lost`. Keep retries idempotent, recheck stock atomically when reserving, and commit mock payment, stock consumption, and the paid state in one transaction.
5. **Verify against the relevant acceptance checks.** Report what was verified in each PR. For changes that affect the purchase path, cover the relevant [acceptance checks](./INITIAL_SPEC.md#acceptance-checks), such as duplicate events, below-floor offers, last-unit contention, repeated payment, or checkout expiry.
